## Spindle Docker evidence

Spindle's PR image check runs the shared `ci_docker.yaml` workflow. It builds the production image and runs the repository's smoke script. The build wrapper invokes plain `docker build` and declares no cross-run cache import or export. Within the Rust stage, the Dockerfile copies the workspace source and fixtures before the only `cargo build --release --locked --bin spindle-rust` instruction. A source change invalidates that instruction's layer, and a fresh builder has no compiled dependency layer to reuse. This is a structural source of repeated compilation, even when a PR changes only the web UI and the entire Rust stage would be reusable on a warm builder. [Spindle Dockerfile](https://github.com/whengas/spindle/blob/8e689b9/Dockerfile) · [Spindle build wrapper](https://github.com/whengas/spindle/blob/8e689b9/.shared/check-docker-images.py) · [GAT Docker CI](https://github.com/jr200-labs/github-action-templates/blob/c962d88/.github/workflows/ci_docker.yaml) · [Docker layer invalidation](https://docs.docker.com/build/cache/optimize/#use-cache-mounts)

| Measure | Earlier PR | PR #249 |
| --- | ---: | ---: |
| Image build and smoke step | 5m 18s | Cancelled at the 10m limit |
| Rust release build layer | 2m 50s | Still running at 8m 19s |
| First dependency compile, from start of Cargo layer | 9.2s | 22.4s |
| `opentelemetry-otlp` compile start, from start of Cargo layer | 53.4s | 6m 26s |
| Spindle backend compile start, from start of Cargo layer | 1m 32s | No matching log before cancellation |

The PR heads have identical Dockerfile, Cargo manifests, lockfile and Rust source inputs. Both runs used the same Rust base image digest, logged 199 Cargo downloads and showed zero BuildKit cache hits. The spread was already visible during dependency compilation. The slow log contains no completed Cargo release build or smoke result and provides no evidence that final linking caused the timeout. Runner CPU contention, quota or I/O could explain slower cold builds. Historical resource metrics for those jobs were unavailable. [Successful job](https://github.com/whengas/spindle/actions/runs/46026413871/job/140598840732) · [Cancelled job](https://github.com/whengas/spindle/actions/runs/46094189690/job/140821689780)

The follow-up Docker job waited 8m 19s before a runner started. The active runner and its Docker-in-Docker sidecar had no resource requests or limits, and Kubernetes classified the pod as BestEffort. Its startup probes included transient Docker readiness failures before the job began. These observations warrant measuring scheduling, readiness and runtime separately. They do not establish the cause of earlier compile variance. [Follow-up Docker job](https://github.com/whengas/spindle/actions/runs/46096775501/job/140829825075)

The parallel host Rust job missed its cache and spent 2m 12s in the post-cache step saving a 338 MB archive. The following baseline should report cache transfer costs separately from compilation for both lanes. [Host Rust job](https://github.com/whengas/spindle/actions/runs/46094189680/job/140821689878)

## Proposed pilot

1. Split Spindle's Rust stage into dependency preparation and application build. Use pinned cargo-chef to prepare a workspace recipe and cook the locked release dependencies before copying the app source and fixtures into the final build stage. Keep the toolchain, working directory, target, profile, feature selection and Cargo flags compatible across cook and build. Verify the resulting production image with the existing smoke test. A UI-only edit should reuse the whole Rust stage, a Rust-only edit should reuse the dependency layer, and a dependency or toolchain change should rebuild what it invalidates. The current multi-stage image already copies the binary into a runtime stage, so this change targets build time. [cargo-chef Docker pattern and caveats](https://github.com/LukeMathWalker/cargo-chef#how-to-use)
2. Teach GAT PR image checks to import the build cache on fresh runners and load the resulting image for the existing smoke checks. The release workflow already knows how to select managed remote BuildKit and fall back to per-job Buildx. Reuse that backend selection contract where the PR runner trust policy allows it. With per-job Buildx, pilot an external cache using `mode=max` so intermediate dependency layers can be restored. Use separate scopes per repository, image and platform. Benchmark the managed backend and the fallback independently. Preserve the image catalog, build contexts and one build per image. [GAT release workflow](https://github.com/jr200-labs/github-action-templates/blob/c962d88/.github/workflows/build_docker_image_multiplatform.yaml) · [Docker external cache](https://docs.docker.com/build/cache/backends/#cache-mode) · [Docker remote driver](https://docs.docker.com/build/builders/drivers/remote/)
3. Seed the cache with a trusted default-branch build. For a GitHub Actions cache backend, a cache written under a PR merge ref helps reruns of that PR. Other PRs can restore the applicable default/base cache. For a registry-backed cache, use a scoped trusted writer and read-only PR access where available. Treat cache as a disposable optimization and keep credentials out of exported layers. Prefer reusable dependency layers over relying on `RUN --mount=type=cache` alone, since the GitHub Actions BuildKit exporter does not preserve those mounts by default. [GitHub cache scoping](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache) · [Docker GHA cache scopes](https://docs.docker.com/build/cache/backends/gha/#scope) · [Docker cache mounts in Actions](https://docs.docker.com/build/ci/github-actions/cache/#cache-mounts)

Measure cache import and export wall time, queue, setup, image build, image load and smoke separately. Capture initial cold, unchanged warm, UI-only, Rust-only and manifest-change runs on the same runner class and toolchain. Repeat on fresh builders to verify cross-job reuse. Use the same native platform and pin the builder image digest for the comparison. Collect runner CPU requests, quota and usage, cgroup throttling, memory pressure and disk I/O while compilation is active, and collect Cargo `--timings` from the build stage to identify the critical crate chain and code generation time. Accept the pilot when both expected warm cache hits occur, the smoke result is equivalent, fresh misses still work, and saved compile time exceeds cache transfer cost. Report runner job time and total time separately. [Cargo build timing report](https://doc.rust-lang.org/cargo/reference/timings.html)

## GAT Rust lanes after the pilot

| Proposal | Where it fits |
| --- | --- |
| `Swatinem/rust-cache` | GAT already uses v2.9.3 for host Rust CI. It keys on compiler and dependency inputs, caches compiled dependencies and disables incremental compilation. It does not provide artifacts to the Alpine container build. Measure restore/save bytes and timings. Trial default-branch-only saves with `save-if` once a trusted default-branch build warms the cache, or registry-only Cargo caching where target archive transfer costs more than rebuilding. [rust-cache v2.9.3](https://github.com/Swatinem/rust-cache/tree/v2.9.3#cache-details) |
| `CARGO_INCREMENTAL=0` | Host CI already gets it from rust-cache. Cargo's default release profile also has incremental disabled. Keep it for an sccache lane. [Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html#release) · [sccache Rust support](https://github.com/mozilla/sccache/blob/main/docs/Rust.md) |
| sccache | Pilot a remote per-compilation cache when compiler timings show persistent work across images, lockfile updates or runners that cannot reuse an entire layer. Set `RUSTC_WRAPPER=sccache`, measure hits, misses, non-cacheable invocations and transfer overhead, and keep target/ABI/toolchain compatible. Final binary links and other crates that invoke the system linker are outside its Rust cache coverage. Avoid paying to move the same artifacts through multiple caching layers without measurements. [sccache Rust support](https://github.com/mozilla/sccache/blob/main/docs/Rust.md) |
| `cargo check`, Clippy and builds | Keep Clippy as GAT's fast check and keep tests and the production image smoke gate. Check skips final code generation, so it cannot provide a runnable binary or confirm codegen/link success. Review the standalone host `cargo build` per consumer for coverage that tests and production image builds already provide. Keep format, lint and test on one runner while they benefit from one toolchain setup and dependency cache. Split jobs when measurements show that parallelism outweighs runner queue, setup and retransfers. [GAT Rust CI](https://github.com/jr200-labs/github-action-templates/blob/c962d88/.github/workflows/ci_rust.yaml) · [Cargo check](https://doc.rust-lang.org/cargo/commands/cargo-check.html) |
| nextest | Pilot when execution of compiled tests dominates. It still builds test binaries and then schedules individual tests as processes. Preserve stable doctests with `cargo test --doc`. It has no effect on the release compiler stage in the image check. [nextest design](https://nexte.st/docs/design/how-it-works/) · [nextest doctest support](https://nexte.st/docs/running/) |
| lld, mold, nightly frontend and generic sharing | Measure linking on the real target first. Rust 1.90 already defaults to LLD on x86-64 GNU/Linux. Spindle's Alpine image uses a different target environment, so verify the actual linker, ABI and runtime output if testing a change. The Rust compiler team enabled the parallel frontend on nightly in November 2026 and replaced the old tuning guidance with `--jobs-frontend`. Gains vary with Cargo's existing parallelism, code generation and memory. Keep these as per-target experiments with a stable baseline. Generic sharing alters inlining and can change binary size, so assess runtime and size as well as build time if evaluating it. [Rust stable LLD rollout](https://blog.rust-lang.org/2025/09/01/rust-lld-on-1.90.0-stable/) · [November 2026 frontend update](https://blog.rust-lang.org/2026/11/16/enabling-parallel-frontend-on-nightly/) · [Rust compiler discussion on generic sharing](https://github.com/rust-lang/rust/issues/142164) |

Standardize the cache contract, logs and smoke semantics in GAT after the pilot. Keep Rust-specific dependency layering in each Dockerfile, where workspace, target and release inputs can be reviewed. Use the repository's pinned stable compiler for production acceptance and align the host CI primary lane with that pin, with any latest-stable compatibility lane evaluated separately. Publish images by building each required platform under its own compatible cache scope, with native runners preferred when profiling finds emulation significant. GitHub Actions cache space and retention are finite, so compare build minutes saved with the storage and runner cost before expanding writes across repositories. [GitHub cache limits](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#usage-limits-and-eviction-policy) · [Docker multi-platform builds](https://docs.docker.com/build/building/multi-platform/)
